# 0.1.0-dev.22 Secure Boot

## Goal

AegisPXE 0.1.0-dev.22 introduces an explicit, fail-closed Secure Boot provisioning policy without changing the known-good Debian Installer initrd or Preseed transport restored in dev.21.

The intended x86-64 UEFI chain is:

```text
UEFI Secure Boot firmware
  -> official iPXE v2.0.0 ipxe-shim.efi
  -> official signed iPXE v2.0.0 ipxe.efi
  -> AegisPXE discovery + policy gate
  -> verified Debian 13 kernel + native initrd.gz
  -> Debian bootnetx64.efi supplied to iPXE's shim command
  -> final one-shot Preseed handoff
  -> Debian Installer
  -> installed Debian shim/grub/kernel on local reboot
```

The reporter remains outside this path. Secure Boot does not reintroduce any of the failed dev.14-dev.20 initramfs injection strategies.

## iPXE first-stage trust

The package build consumes the official iPXE v2.0.0 `ipxeboot.tar.gz` release bundle and pins the tag to commit:

`12798ec29aa8a64d8675c4378b99f5fe28447afb`

The build helper:

1. reads the public GitHub release metadata for exactly `v2.0.0`,
2. confirms the tag still resolves to the pinned commit,
3. requires one uploaded `ipxeboot.tar.gz` asset at the expected GitHub URL,
4. requires GitHub to publish a SHA-256 digest and a bounded asset size,
5. downloads the asset over HTTPS and verifies that digest and size,
6. extracts only `x86_64-sb/ipxe-shim.efi` and `x86_64-sb/ipxe.efi`, rejecting symlink/link/non-regular members,
7. requires both PE files to contain Authenticode signature tables via `sbverify`,
8. writes a package manifest with the release, commit, release-asset SHA-256 and per-file SHA-256/size.

At runtime the server independently hashes the installed assets against the package manifest. With `AEGISPXE_SECURE_BOOT_POLICY=required`, missing, symlinked, modified, malformed or unpinned Secure Boot assets prevent the service from starting.

The package installs these assets to the TFTP root as:

- `ipxe-shim.efi`
- `ipxe.efi`

The DHCP server must hand UEFI Secure Boot clients `ipxe-shim.efi`, not `ipxe.efi`. The iPXE shim then verifies and loads the matching second stage.

## Firmware observation and policy

Discovery records the iPXE UEFI settings:

- `efi/SecureBoot`
- `efi/SetupMode`

They are normalized to one of:

- `enabled`
- `disabled`
- `setup_mode`
- `unknown`
- `unsupported`

The state and observation timestamp are persisted on the Machine and emitted in structured logs.

`AEGISPXE_SECURE_BOOT_POLICY` accepts:

- `required`: provisioning is allowed only for state `enabled`,
- `audit`: provisioning remains possible but non-enabled observations emit warnings,
- `disabled`: Secure Boot observation does not gate provisioning.

The packaged/default policy is `required`.

This observation is a policy signal, not remote attestation. AegisPXE does not claim that a query-string report of `efi/SecureBoot=1` is cryptographic proof by itself. The security boundary comes from the actual UEFI signature enforcement plus the signed iPXE and Debian shim chains. A future TPM/PCR attestation design may add independent cryptographic evidence.

## Debian driver v2

Driver contract `debian13` is bumped from version 1 to version 2. New InstallationSpecs pin exactly three Debian artifacts from one verified Debian release/installer provenance:

- `linux`
- `initrd.gz`
- `bootnetx64.efi`

All three are selected from Debian's signed `InRelease` metadata and verified `SHA256SUMS` chain before the immutable InstallationSpec is created.

The boot script retains the dev.21 working installer payload while enforcing a precise one-shot ordering:

```text
kernel
native initrd.gz
shim bootnetx64.efi
preseed.cfg
boot
```

`bootnetx64.efi` must be fetched and configured before `preseed.cfg`. Successful Preseed delivery atomically consumes the one-shot Assignment, so moving the shim fetch after Preseed would reject that artifact as no longer assignment-authorized.

There is no generated initramfs, no reporter overlay and no multi-initrd EFI experiment.

## Logging

Expected successful startup fields include:

```text
component=boot.secureboot
operation=validate_assets
secure_boot_policy=required
upstream_release=v2.0.0
upstream_commit=12798ec29aa8a64d8675c4378b99f5fe28447afb
release_asset_sha256=sha256:...
ipxe_shim_sha256=sha256:...
ipxe_sha256=sha256:...
result=success
```

Machine discovery and boot decisions include `firmware`, `secure_boot_state` and `secure_boot_policy`. Required-policy failures use `SEC023_SECURE_BOOT_REQUIRED`. Invalid firmware observations use `SEC024_SECURE_BOOT_EVIDENCE_INVALID`. Invalid packaged signed assets use `SEC025_SECURE_BOOT_ASSETS_INVALID`.

## Required real E2E before merge

The Secure Boot change is not complete until all of the following succeed on the real Proxmox fixture:

1. OVMF/UEFI Secure Boot enabled with the Microsoft third-party UEFI CA available.
2. DHCP filename changed to `ipxe-shim.efi` for UEFI clients.
3. Firmware starts the official iPXE shim and the signed iPXE second stage.
4. Discovery persists `secure_boot_state=enabled`.
5. A new Debian driver-v2 InstallationSpec is armed.
6. Debian Installer starts and completes using the unchanged native initrd/Preseed transport with the Debian shim fetched before the final Preseed handoff.
7. Local reboot succeeds while Secure Boot remains enabled.
8. SSH key login to the installed host succeeds.
9. A negative fixture with Secure Boot disabled or SetupMode active does not receive installation boot material under `required` policy and records `SEC023_SECURE_BOOT_REQUIRED`.
10. Modifying either packaged/TFTP Secure Boot binary is detected by package refresh/runtime validation as appropriate.

The dev.23 Proxmox positive fixture has now proven items 1-8 once. Negative fixtures, tamper behavior, repeatability and the RC upgrade matrix remain release gates.
