# 0.1.0 Debian 13 Standard: BootSpec contract

`0.1.0-dev.3` introduced the typed `BootSpec` as a deterministic derivative of an immutable `InstallationSpec`. `0.1.0-dev.6` connects that contract to the assignment-gated iPXE transport.

## Separation

The two specifications have different jobs:

- `InstallationSpec` is the authoritative immutable provisioning assignment: machine, driver contract, OS target, profile revision, verified artifact provenance, storage/security intent and lifecycle credential identity.
- `BootSpec` is transport-facing data only: installation identity, driver contract identity, digest-pinned kernel/initrd references, bounded kernel arguments and a non-secret relative seed reference.

A `BootSpec` is not a second source of truth and is not persisted independently. It is re-rendered from the immutable InstallationSpec by the pinned driver contract.

## Debian 13 rendering

The Debian 13 driver contract currently has:

- driver ID `debian13`,
- driver contract version `1`, independent from the AegisPXE application version,
- target Debian `13` on `amd64`,
- exactly one `linux` artifact,
- exactly one `initrd.gz` artifact,
- relative seed reference `preseed.cfg`.

Before rendering, the driver requires both artifacts to:

- pass the generic InstallationSpec artifact contract,
- use the same pinned Debian installer version,
- use identical Debian `trixie` provenance,
- originate from the trusted `https://deb.debian.org` origin,
- have source paths matching their pinned installer version and artifact role.

A mismatched driver contract version or mixed artifact set fails closed.

## BootSpec bounds

A BootSpec:

- contains exactly one kernel reference,
- contains one to four initrd references,
- contains at most 32 bounded kernel arguments,
- rejects duplicate artifact IDs and duplicate kernel argument keys,
- rejects secret-looking argument keys,
- contains no upstream artifact URL,
- contains no lifecycle credential value,
- uses a bounded relative seed reference without query string or fragment.

The current Debian renderer emits only static public kernel arguments (`auto=true`, `priority=critical`, `interface=auto`).

## Assignment-gated transport

`0.1.0-dev.6` makes a BootSpec executable only after the public-boot trust gate succeeds:

- Machine policy is `provision`,
- an Assignment for the exact Machine and InstallationSpec is currently `armed`.

Discovery then returns an iPXE chain to `/boot/installations/{installation_id}/boot.ipxe`.

The installation boot script maps the BootSpec references to assignment-gated HTTP reads for:

- `artifacts/linux`,
- `artifacts/initrd.gz`,
- the relative `preseed.cfg` SeedRef.

iPXE loads the normal Debian initrd and injects the fetched `preseed.cfg` as `/preseed.cfg` in its magic initrd. The script never contains a lifecycle credential, bearer token or Debian `preseed/url` parameter.

Kernel arguments are rendered through a strict character allowlist before they enter iPXE syntax. A future driver cannot silently inject shell/iPXE control syntax through a BootSpec argument.

## Artifact integrity

The public artifact endpoints never proxy a caller-supplied URL. They load the immutable InstallationSpec, validate the Debian driver contract, select only the pinned `linux` or `initrd.gz` Descriptor, and pass that Descriptor to the verified artifact loader.

The loader checks the pinned source boundary, response size and SHA-256 before bytes are returned.

## Lifecycle rule

Discovery chaining, rendering the installation boot script, fetching kernel/initrd, and rendering/fetching Preseed are retryable reads. None of them imply `INSTALLER_STARTED`, append runtime lifecycle progress or consume the Assignment.

The Assignment remains armed until a later cryptographically authenticated installer-start operation is accepted according to `LIFECYCLE.md`.

## Remaining boundary

This slice intentionally does not:

- release lifecycle credential values,
- authenticate installer telemetry,
- cryptographically attest the booting Machine,
- expose administrative create/approve/arm/cancel HTTP mutations,
- mark any installer lifecycle stage.

Those operations remain behind the cryptographic boot-trust and authenticated operator boundaries defined by the project security model.
