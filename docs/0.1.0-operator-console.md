# 0.1.0 Operator Console, listener roles and Debian Standard wizard

`0.1.0-dev.8` introduced the authenticated Operator Console and Debian 13 Standard InstallationSpec wizard. `0.1.0-dev.9` separates the PXE and Studio network surfaces, adds an explicit trusted-reverse-proxy contract for SSO deployments, and makes the Debian late hook locally observable.

## Separate listener roles

AegisPXE deliberately gives PXE transport and browser administration different HTTP surfaces even though they run in one control-plane process.

Default package configuration:

```text
AEGISPXE_PXE_LISTEN=0.0.0.0:8090
AEGISPXE_STUDIO_LISTEN=127.0.0.1:8091
AEGISPXE_DB=/var/lib/aegispxe/aegispxe.db
AEGISPXE_OPERATOR_KEY=/var/lib/aegispxe/operator.key
AEGISPXE_TRUSTED_PROXY_CIDRS=
AEGISPXE_TRUSTED_PROXY_IDENTITY_HEADER=X-Remote-User
AEGISPXE_TRUSTED_PROXY_PROTO_HEADER=X-Forwarded-Proto
```

`AEGISPXE_PXE_LISTEN` is intentionally network reachable by default because firmware/iPXE clients must reach it. Its HTTP allowlist contains health, discovery and `/boot/` provisioning material. Studio, Machine inventory and operator routes are not exposed on this listener.

For upgrade compatibility, the legacy `AEGISPXE_LISTEN` value is used when `AEGISPXE_PXE_LISTEN` is not set.

`AEGISPXE_STUDIO_LISTEN` serves the browser surface. The default remains loopback so the bootstrap operator key can be used locally or through an SSH tunnel without exposing the administration listener to the provisioning network. The legacy `AEGISPXE_OPERATOR_LISTEN` value remains a fallback when the new variable is absent.

A non-loopback Studio bind is rejected unless Trusted Proxy configuration is enabled. Hostnames are not accepted as bind trust boundaries; use an explicit IP literal. `AEGISPXE_STUDIO_LISTEN=disabled` disables the browser listener entirely.

The Studio surface exposes `/ui/`, read-only Machine inventory APIs and health. It does not expose `/boot/` or discovery endpoints. The Studio root redirects to the authenticated Operator Console so deployments behind SSO present one primary control surface rather than separate operator and observation landing pages.

## Reverse proxy / SSO trust

AegisPXE does not implement or store the reverse proxy's Passkey/WebAuthn credentials. TLS termination, Passkey policy and user authentication can remain in the reverse proxy/SSO layer.

AegisPXE trusts an asserted proxy identity only when **all** of these conditions hold:

- the direct TCP peer is inside `AEGISPXE_TRUSTED_PROXY_CIDRS`,
- the configured protocol header has the exact value `https`,
- the configured identity header contains a bounded non-empty identity.

Both header names are configuration. No reverse-proxy hostname, public domain or fixed Studio URL is compiled into AegisPXE.

The proxy must overwrite or remove client-supplied versions of the configured identity/protocol headers before forwarding to AegisPXE. A request from any non-trusted direct peer is rejected even if it forges identical header names and values.

After the trusted boundary accepts an identity, AegisPXE issues its normal short-lived server-side operator session and per-session CSRF token. Audit actors use the form `proxy:<asserted identity>`. Session tokens and CSRF values are not log fields.

When Trusted Proxy configuration is active, the Studio listener accepts only loopback requests or requests satisfying the Trusted Proxy contract. This application-level gate complements, rather than replaces, host firewall rules that should restrict the backend port to the reverse proxy where possible.

The local bootstrap key remains a recovery mechanism on loopback:

```bash
ssh -L 8091:127.0.0.1:8091 <admin>@<aegispxe-host>
```

Then use the local Studio listener and `/ui/operator/login` with the key stored at `/var/lib/aegispxe/operator.key`.

## Public origins are deployment configuration

AegisPXE generates browser links as relative paths and generates PXE boot URLs from the actual PXE request. A domain such as `pxe.example.net` therefore belongs to reverse-proxy/DNS configuration, not application source code.

A later installer telemetry API may intentionally be exposed through the same external origin as Studio. Such installer endpoints must be excluded from interactive proxy authentication only when they are protected by AegisPXE's installation-scoped cryptographic trust. Operator SSO identity and installer trust are separate security boundaries.

## Operator Console

`/ui/operator/` exposes only the provisioning mutations required by the Debian 13 Standard vertical slice:

- set Machine policy to `pending`, `local`, `provision` or `blocked`,
- create a Debian 13 Standard immutable InstallationSpec,
- arm an unassigned InstallationSpec for its Machine,
- cancel an armed assignment,
- end a local bootstrap session.

A cancelled or consumed InstallationSpec is not recycled. A new provisioning attempt receives a new immutable InstallationSpec.

Every accepted store mutation retains the authenticated actor and the same request ID used by the operator HTTP request.

## Debian 13 Standard wizard

The wizard is intentionally not an arbitrary InstallationSpec editor.

The operator supplies only desired state that belongs in the resolved ProfileSnapshot or concrete installation target:

- eligible `provision` Machine,
- hostname,
- locale,
- keyboard layout,
- timezone,
- key-only administrator identity,
- one or more SSH public keys,
- optional additional Debian packages,
- explicit whole-device target disk.

Driver ID/version, Debian release, architecture, trusted artifact source, installer version, hashes, provenance, Standard security baseline, lifecycle credential identity, InstallationSpec ID and creation time remain server-owned.

Before any Debian metadata or artifact download, AegisPXE validates the selected Machine, ProfileSnapshot and target whole-disk path. A partition such as `/dev/vda1` fails before artifact resolution.

After local input validation, the normal Debian artifact resolver verifies the signed `trixie/InRelease` trust chain, checksum manifest and final kernel/initrd bytes. Only those verified descriptors enter the immutable InstallationSpec.

Creating the spec does **not** arm it. Creation and arming remain separate explicit actions.

## Debian finish / late-hook diagnostics

Debian's native `finish-install/reboot_in_progress` preseed answer remains responsible for suppressing the normal final completion prompt. AegisPXE does not bypass installer errors to force a reboot.

The AegisPXE late hook is fail-closed because it installs and validates security-sensitive SSH/sudo state. `0.1.0-dev.9` makes that hook observable and prepares OpenSSH's runtime state before validation:

- `/run/sshd` is created in the target before `sshd -t`,
- host keys are ensured with `ssh-keygen -A`,
- sudoers and sshd validation receive step markers,
- the complete hook records start/final result and exit status.

The log path is:

```text
# while Debian Installer still owns /target
/target/var/log/aegispxe-installer.log

# after the installed system boots
/var/log/aegispxe-installer.log
```

No `|| true` or equivalent is used to hide a failed hardening/validation step. If d-i returns to its main menu again, the last `result=started` step plus the final `rc=` identifies the failing boundary for the next fix.

## Response bounds

Each Debian upstream HTTP operation remains bounded to two minutes. Artifact resolution performs multiple signed-metadata and artifact requests sequentially, so the AegisPXE HTTP server uses a ten-minute write timeout for the complete bounded request path.

Operator form bodies remain bounded at 96 KiB.

## Observability

Authentication/session decisions use `component=operator.auth`. Trusted proxy gating uses `component=operator.proxy`. Wizard activity uses `component=operator.installation`.

Useful normal fields include `request_id`, Machine/Installation IDs, actor, result, duration and stable error/cause information. Bootstrap keys, session tokens, CSRF tokens, SSH public-key payloads and artifact bytes are not intentional log fields.

## Lifecycle boundary

Creating, reviewing or arming an InstallationSpec still does not invent installer progress. Public boot reads remain retryable and non-consuming. `INSTALLER_STARTED` is emitted only after the later authenticated installer telemetry boundary accepts a real start report.

Cryptographic boot trust is still required before lifecycle-credential release or any other secret-bearing installer operation.
