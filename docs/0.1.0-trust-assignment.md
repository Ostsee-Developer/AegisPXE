# 0.1.0 Debian 13 Standard: trust and assignment

`0.1.0-dev.5` introduces the provisioning trust and assignment foundation required before AegisPXE may expose a real installer boot path.

## Layered trust

AegisPXE deliberately separates four facts:

1. discovery identity resolves a network observation to a Machine record,
2. operator approval expresses administrative intent to provision that Machine,
3. an armed Assignment selects exactly one immutable InstallationSpec,
4. cryptographic boot trust authenticates a client for secret-bearing operations.

MAC addresses and SMBIOS UUIDs participate only in layer 1. They never satisfy layer 4.

## Assignment contract

An Assignment binds one Machine to one InstallationSpec and records:

- server-assigned assignment ID,
- Machine ID,
- InstallationSpec ID,
- state,
- cryptographic trust requirement,
- arm timestamp and actor,
- optional consumed/cancelled timestamp.

States are `armed`, `consumed` and `cancelled`.

At most one Assignment may be armed for a Machine. An InstallationSpec is assigned at most once. A different provisioning attempt creates a different InstallationSpec.

Arming requires:

- the Machine exists,
- the Machine policy is `provision`,
- the InstallationSpec exists,
- the InstallationSpec belongs to that exact Machine,
- no other Assignment for the Machine is armed.

Arming emits `INSTALLATION_ARMED`. Cancellation emits `INSTALLATION_ASSIGNMENT_CANCELLED`. Consumption is reserved for the later authenticated installer-start path and is not exposed by dev.5.

## Trust gate

The pure trust gate projects two separate authorizations:

### Public boot material

May become eligible when:

- operator approval is present,
- the correct InstallationSpec is armed.

This category must contain no reusable secret. Debian kernel/initrd, immutable public configuration and SSH public keys may live here once the transport is implemented.

### Secret release

Requires all public-boot conditions plus cryptographic boot trust. Lifecycle credentials, authenticated installer APIs and any future secret-bearing material stay blocked without that proof.

Dev.5 has no cryptographic verifier yet, so Studio correctly shows secret release as blocked.

## Debian seed decision

Debian supports initrd preseeding. AegisPXE therefore prefers placing the rendered non-secret `preseed.cfg` inside a per-installation initrd derivative rather than introducing a network Preseed URL that would require a new credential transport.

The lifecycle credential is not placed in the Preseed, BootSpec arguments, public boot scripts, URLs or machine metadata.

## Studio

Studio now exposes read-only InstallationSpec and trust views:

- installation inventory,
- Machine/driver/profile binding,
- target disk and security intent,
- resolved ProfileSnapshot,
- verified artifact metadata,
- Assignment state,
- operator approval state,
- public-boot gate,
- cryptographic-trust requirement,
- secret-release gate,
- installation audit timeline.

SSH public-key payloads and lifecycle credential identifiers are intentionally not rendered into the browser.

No approve/arm/cancel control is exposed until operator authentication and authorization exist.

## Observability

Assignment arm/cancel operations log:

- component and operation,
- request ID,
- Machine ID,
- Installation ID,
- Assignment ID when allocated,
- actor,
- result,
- stable error code for rejected/conflicting operations.

No lifecycle credential value, SSH key or other secret is logged.

## Next gate

The next vertical slice may construct a per-installation initrd derivative and serve non-secret boot material only for an operator-approved Machine with the correct armed Assignment. Secret release and authenticated installer telemetry remain blocked until cryptographic boot trust is implemented and proven.
