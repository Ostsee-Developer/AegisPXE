# 0.1.0 Operator authentication

`0.1.0-dev.7` introduced the minimum authenticated administrative boundary required for the Debian 13 vertical provisioning path. `0.1.0-dev.9` keeps that local bootstrap mechanism as recovery while adding an explicitly trusted reverse-proxy/SSO path for normal Studio access.

This is still intentionally narrower than the eventual AegisPXE user/RBAC system.

## Bootstrap key

At startup AegisPXE loads or creates a random 256-bit base64url bootstrap operator key. The default path is:

```text
/var/lib/aegispxe/operator.key
```

The path may be changed with `AEGISPXE_OPERATOR_KEY`, but it must be absolute.

The key file contract is strict:

- regular file only,
- symlinks are rejected,
- no group/other permissions,
- newly generated files use mode `0600`,
- the key value is never intentionally logged.

The service log records only whether the key was created/loaded and its filesystem path.

An administrator with host-root authority may read the initial key explicitly when recovery/local bootstrap access is needed:

```sh
sudo cat /var/lib/aegispxe/operator.key
```

## Sessions

All accepted human authentication paths end in the same AegisPXE browser-session contract:

- cryptographically random server-side session,
- 8-hour expiry,
- per-session CSRF value,
- HttpOnly, SameSite=Strict browser cookie,
- Secure cookie when the external/request trust boundary is HTTPS.

Server-side lookup stores only a SHA-256 index of the random session token. Bootstrap keys, SSO credentials, session tokens and CSRF values are never intentional log fields.

## Direct/local bootstrap transport

The bootstrap key is accepted only over:

- direct TLS established by AegisPXE, or
- loopback for local administration / SSH port forwarding.

Direct cleartext non-loopback bootstrap login or mutation remains rejected.

## Trusted reverse-proxy / SSO transport

`0.1.0-dev.9` permits a reverse proxy to authenticate human operators without requiring AegisPXE to store the proxy's Passkey/WebAuthn credentials.

Configuration:

```text
AEGISPXE_TRUSTED_PROXY_CIDRS=
AEGISPXE_TRUSTED_PROXY_IDENTITY_HEADER=X-Remote-User
AEGISPXE_TRUSTED_PROXY_PROTO_HEADER=X-Forwarded-Proto
```

When `AEGISPXE_TRUSTED_PROXY_CIDRS` is empty, proxy-header authentication is disabled.

When enabled, AegisPXE accepts the asserted identity only if:

1. the direct TCP peer is inside a configured trusted proxy network/address,
2. the configured protocol header is exactly `https`,
3. the configured identity header is non-empty and within input bounds.

The header names are configurable. A forged header from another direct LAN peer is not authentication.

The reverse proxy must overwrite/remove client-supplied versions of the configured identity and protocol headers before forwarding to AegisPXE.

A trusted proxy identity creates a normal AegisPXE session with actor `proxy:<identity>`. CSRF remains mandatory for mutations.

See `docs/adr/0004-studio-trusted-proxy.md`.

## Studio network gate

The Studio listener remains loopback by default. A non-loopback bind is accepted only when Trusted Proxy configuration is enabled.

With Trusted Proxy mode active, Studio accepts only:

- loopback recovery traffic, or
- requests satisfying the trusted proxy identity/HTTPS contract.

This application gate should be combined with firewall rules restricting the Studio backend port to the reverse proxy where practical.

PXE traffic has a separate listener/path surface and is never authenticated as a human operator merely because it shares the same AegisPXE process.

## Login abuse protection

Bootstrap-key login attempts are bounded per remote source:

- five failed attempts,
- one-minute window,
- fail closed after the limit,
- stable `SEC003_OPERATOR_AUTH_RATE_LIMITED` logging.

The supplied bootstrap key is never included in the rejection log.

The reverse proxy/SSO layer owns its own Passkey/login abuse controls before it asserts an identity to AegisPXE.

## CSRF

Every authenticated mutation requires the CSRF value bound to the server-side AegisPXE session. A valid session cookie without the correct CSRF value is rejected with `SEC005_OPERATOR_CSRF_INVALID` before domain mutation.

## Mutation surface

The authenticated wrapper currently exposes the narrow provisioning operations needed by the Debian Standard path:

- set Machine policy,
- create an immutable Debian 13 Standard InstallationSpec through the server-owned wizard,
- arm an existing InstallationSpec,
- cancel an armed Installation assignment.

Creating and arming remain separate actions.

## Audit and logging

Authentication decisions use structured logs with request ID, direct remote source, actor after authentication, result and non-secret cause/error code.

Authorized Store mutations receive the same request ID and actor (`bootstrap:operator` or `proxy:<identity>`), so the authentication decision can be correlated with the resulting Machine/Installation audit event.

Never log:

- bootstrap operator key,
- reverse-proxy Passkey/WebAuthn credential,
- session cookie value,
- CSRF value.

## Limits

Human operator authentication does not:

- authenticate a booting Machine,
- satisfy cryptographic boot trust,
- release lifecycle credentials,
- authenticate installer telemetry,
- expose recovery material.

A future installer API may share an external DNS origin with Studio, but it must use installation-scoped cryptographic authorization rather than reverse-proxy operator SSO.
