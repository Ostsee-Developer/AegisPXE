# 0.1.0 Operator authentication

`0.1.0-dev.10` completes the human authentication boundary for the `0.1.0` vertical slice. The trusted reverse proxy remains the outer identity boundary, but a proxy identity no longer creates an AegisPXE operator session by itself. AegisPXE now requires its own WebAuthn/Passkey proof and owns authorization state independently.

This human operator trust is separate from Machine discovery identity and from installation-scoped cryptographic trust.

## Normal authentication chain

The normal browser path is intentionally layered:

```text
reverse proxy authentication
        -> trusted external subject
        -> AegisPXE user lookup
        -> AegisPXE WebAuthn/Passkey
        -> AegisPXE role/status authorization
        -> server-side AegisPXE session
```

The reverse proxy answers only the outer identity question. It does not grant an AegisPXE role and cannot issue an AegisPXE session.

AegisPXE currently supports two roles:

- `admin`
- `operator`

and four account states:

- `pending_review`
- `enrollment_required`
- `active`
- `blocked`

## Trusted reverse-proxy identity

Configuration:

```text
AEGISPXE_TRUSTED_PROXY_CIDRS=
AEGISPXE_TRUSTED_PROXY_IDENTITY_HEADER=Remote-User
AEGISPXE_TRUSTED_PROXY_PROTO_HEADER=X-Forwarded-Proto
```

When `AEGISPXE_TRUSTED_PROXY_CIDRS` is empty, proxy identity assertions are disabled.

When enabled, AegisPXE accepts an asserted external subject only when:

1. the direct TCP peer is inside an explicitly configured trusted proxy address/network,
2. the configured protocol header is exactly `https`,
3. the configured identity header is non-empty, bounded and free of control characters.

The reverse proxy must overwrite or remove client-supplied versions of the configured headers before forwarding.

A trusted source may reach the Studio backend without an identity, for example a health check or the explicitly gated emergency recovery page. Lack of an identity never creates an operator session.

The external identity is stored as provider plus subject. The subject is not reused as the WebAuthn user handle. AegisPXE allocates a separate random stable handle so browser credential identity is not coupled to a visible username.

## New-user review

The first time a valid trusted external subject reaches AegisPXE, it is recorded as:

```text
pending_review
```

If an administrator already exists, the new identity receives no provisioning privileges and can only wait for review.

An administrator may approve the identity as `operator` or `admin`. Approval changes the state to:

```text
enrollment_required
```

The user must then enroll an AegisPXE Passkey before becoming:

```text
active
```

A blocked user cannot authenticate. The Store prevents blocking the last non-blocked administrator.

## Initial administrator

The first trusted identity is not made administrator merely because it arrived first.

When no AegisPXE administrator exists, that pending identity may claim the initial administrator role only after proving the local recovery key. The account then enters `enrollment_required` and still has to enroll an AegisPXE Passkey before an operator session can exist.

The recovery key therefore bootstraps authorization; it is not a web password.

## AegisPXE WebAuthn configuration

WebAuthn deployment properties are configuration, never compiled hostnames:

```text
AEGISPXE_WEBAUTHN_RP_ID=
AEGISPXE_WEBAUTHN_ORIGINS=
```

`AEGISPXE_WEBAUTHN_RP_ID` is the WebAuthn relying-party identifier. `AEGISPXE_WEBAUTHN_ORIGINS` accepts one or more allowed origins separated by commas, semicolons or whitespace.

Both values must be configured together. If both are empty, AegisPXE starts with WebAuthn disabled so package installation and recovery configuration remain possible, but Passkey login/enrollment is unavailable.

AegisPXE uses the pinned `go-webauthn` implementation, requires user verification and persists the complete credential state required to validate later assertions, including the credential counter/state maintained by the library.

No public DNS name is hardcoded in source or package defaults.

## Sessions and CSRF

Only an `active` AegisPXE user can receive a browser session.

Normal sessions use authentication method:

```text
zoraxy+passkey
```

Emergency sessions use:

```text
recovery+passkey+key
```

The session contract remains:

- cryptographically random server-side session token,
- 8-hour expiry,
- per-session CSRF value,
- HttpOnly cookie,
- SameSite=Strict,
- Secure cookie on the trusted HTTPS boundary,
- explicit user ID and role in the server-side session.

Browser mutations require the matching CSRF value.

The generic trusted-proxy/session shortcut and recovery-key-only browser login from earlier development slices are removed in dev.10.

## Recovery key

At startup AegisPXE loads or creates a random 256-bit base64url recovery key. The compatibility configuration name remains:

```text
AEGISPXE_OPERATOR_KEY=/var/lib/aegispxe/operator.key
```

The file contract is strict:

- regular file only,
- symlinks rejected,
- no group/other permissions,
- newly generated files mode `0600`,
- value never intentionally logged.

An administrator with host-root authority may read it explicitly:

```sh
sudo cat /var/lib/aegispxe/operator.key
```

Recovery-key verification is constant-time and rate limited per remote source. The key alone cannot create a browser session.

## Emergency authentication

When no trusted external identity is supplied, AegisPXE exposes the emergency authentication path rather than silently weakening the normal path.

All three factors are required:

```text
AegisPXE username/external subject
        + existing AegisPXE Passkey
        + local recovery key
```

The flow is:

1. the operator enters the known AegisPXE subject; accounts are not enumerated,
2. AegisPXE verifies the user's existing Passkey,
3. successful Passkey verification creates a one-time five-minute recovery ticket,
4. the local recovery key is verified,
5. the recovery ticket is consumed,
6. only then is an AegisPXE session created.

Failures use deliberately generic authentication responses where account enumeration would otherwise be possible.

If the reverse proxy process itself is unavailable, the same emergency flow is reachable locally through loopback, for example with an SSH port forward. The recovery design therefore does not require the external proxy to be healthy.

## Studio network gate

The Studio listener remains loopback by default:

```text
AEGISPXE_STUDIO_LISTEN=127.0.0.1:8091
```

A non-loopback Studio bind requires configured trusted-proxy CIDRs. With that mode active, the application-level gate accepts only:

- loopback traffic, or
- a direct peer inside the trusted proxy boundary with forwarded protocol `https`.

Identity is evaluated separately after that network/transport gate. This allows proxy health requests without manufacturing a user identity while still rejecting arbitrary LAN clients.

The backend port should additionally be restricted to the reverse proxy with host/network firewall policy where practical.

The legacy core `/api/v1/machines` inventory is intentionally not exposed by the Studio listener. Inventory used by Studio is served from session-authenticated `/ui/` routes, so source trust cannot bypass the AegisPXE Passkey/session boundary.

## Dashboard authorization

The unified Dashboard replaces the old read-only Studio and separate Operator Console.

Authenticated operators may manage the provisioning operations required by the Debian 13 vertical path, including reviewing Machines, setting non-authoritative nicknames, changing explicit policy, creating immutable InstallationSpecs, and arming/cancelling assignments.

Administrators additionally review/approve/block AegisPXE users and perform destructive Machine/Installation deletion. Deletion requires CSRF protection plus exact-ID confirmation and is guarded against active provisioning ownership.

Creating a specification and arming a destructive next boot remain separate explicit actions.

## Audit and logging

Authentication and authorization decisions emit structured logs with request ID, user ID where known, actor, authentication method, direct remote source where relevant, result and stable non-secret cause/error code.

User discovery, initial-admin claim, approval, blocking and Passkey enrollment also create persistent audit/events where the Store owns the state mutation.

The Dashboard live-log view receives only the already-redacted structured logger output. It is backed by a bounded in-memory ring and does not read raw journal files. NDJSON export contains that same redacted stream.

Never log:

- recovery key,
- WebAuthn private/authenticator material,
- browser session token,
- CSRF value,
- rendered installer seed,
- SSH public-key payload where it would add no operational value.

## Trust boundaries that remain separate

Human operator authentication does not:

- authenticate a booting Machine,
- turn MAC or SMBIOS UUID into authentication,
- satisfy cryptographic boot trust,
- release lifecycle credentials,
- authenticate installer telemetry.

Installer lifecycle/status/log ingestion must use installation-scoped cryptographic authorization once its runtime delivery path is E2E-proven rather than the interactive human authentication chain.
