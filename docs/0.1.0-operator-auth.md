# 0.1.0 Bootstrap operator authentication

`0.1.0-dev.7` introduces the minimum authenticated administrative boundary required for the Debian 13 vertical provisioning path.

It is intentionally a bootstrap mechanism, not the final AegisPXE user/RBAC system.

## Bootstrap key

At startup AegisPXE loads or creates a random 256-bit base64url bootstrap operator key. The default path is:

```text
/var/lib/aegispxe/operator.key
```

The path may be changed with `AEGISPXE_OPERATOR_KEY`, but it must be absolute.

The key file contract is strict:

- regular file only,
- symlinks are rejected,
- no group/other permissions,
- newly generated files use mode `0600`,
- the key value is never intentionally logged.

The service log records only whether the key was created/loaded and its filesystem path.

An administrator with host-root authority may read the initial key explicitly when needed:

```sh
sudo cat /var/lib/aegispxe/operator.key
```

Reading/revealing this file is outside normal Studio behavior. AegisPXE never prints it on startup or in HTTP responses other than the login exchange itself.

## Login and sessions

The bootstrap key is presented only to `/ui/operator/login` over an accepted secure operator transport.

A successful login creates:

- a cryptographically random server-side session,
- an 8-hour expiry,
- a per-session CSRF value,
- an HttpOnly, SameSite=Strict browser cookie,
- the `Secure` cookie attribute when the request itself uses TLS.

The bootstrap key itself is not retained in browser storage after login. Server-side session lookup stores only a SHA-256 index of the random session token.

Logout deletes the server-side session and expires the browser cookie.

## Transport rule

Operator credentials and mutations are refused on cleartext non-loopback network HTTP.

Accepted in this first contract:

- direct TLS (`r.TLS` is established by AegisPXE),
- loopback connections for local administration or an SSH tunnel.

AegisPXE does **not** trust `X-Forwarded-Proto` or similar proxy headers as transport proof in dev.7. A future reverse-proxy integration must identify trusted proxy peers explicitly before forwarded scheme information can affect authentication decisions.

Public Studio views remain available read-only over the configured listener.

## Login abuse protection

Login attempts are bounded per remote source:

- five failed attempts,
- one-minute window,
- fail closed after the limit,
- stable `SEC003_OPERATOR_AUTH_RATE_LIMITED` logging.

The supplied bootstrap key is never included in the rejection log.

## CSRF

Every authenticated mutation requires the CSRF value bound to the server-side session. A valid session cookie without the correct CSRF value is rejected with `SEC005_OPERATOR_CSRF_INVALID` before domain mutation.

## Initial mutation surface

The authenticated wrapper exposes only the narrow mutations already protected by AegisPXE domain contracts:

- set Machine policy,
- arm an existing InstallationSpec,
- cancel an armed Installation assignment.

The public Studio does not render buttons for these routes in dev.7. The next Studio slice can add forms/buttons without weakening the authentication boundary.

Creating a new InstallationSpec from a profile/target selection remains a separate workflow because it also needs artifact resolution, immutable snapshot construction and explicit destructive-disk confirmation.

## Audit and logging

Authentication decisions use structured logs with:

- `component=operator.auth`,
- operation,
- request ID,
- remote source,
- actor after authentication,
- result,
- stable `SECxxx` code for rejection,
- non-secret cause class.

Authorized Store mutations receive the same request ID and the actor `bootstrap:operator`, so the authentication decision can be correlated with the resulting Machine/Installation audit event.

Never log:

- bootstrap operator key,
- session cookie value,
- CSRF value.

## Limits

The bootstrap operator boundary does not:

- authenticate a booting Machine,
- satisfy cryptographic boot trust,
- release lifecycle credentials,
- provide users/roles/passkeys,
- trust reverse-proxy headers,
- expose recovery material.

Those concerns remain separate trust boundaries.
