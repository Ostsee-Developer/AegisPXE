# 0.0.3 Headless Discovery Slice

AegisPXE 0.0.3 is the first complete boot-to-control-plane slice. It deliberately stops before any operating-system installer is exposed.

## Runtime path

```text
firmware
  -> iPXE
  -> GET /boot/discovery.ipxe
  -> GET /api/v1/discovery.ipxe?...
  -> machine identity transaction
  -> MACHINE_DISCOVERED / MACHINE_SEEN event
  -> typed server-side boot decision
  -> exit iPXE provisioning path
```

Unknown machines are created exactly once with policy `pending`. Repeated observations resolve to the same AegisPXE machine ID and update `last_seen`.

## Stage-1 PXE runtime

The Debian package depends on `ipxe` and `tftpd-hpa`. During package configuration AegisPXE reads the existing `TFTP_DIRECTORY` from `/etc/default/tftpd-hpa` and, when it is a safe absolute path, materializes the upstream Debian iPXE assets needed for chainloading:

- `ipxe.efi` for UEFI clients,
- `undionly.kpxe` for legacy BIOS clients.

AegisPXE does not overwrite an existing destination file when its content differs from the packaged iPXE asset, and it does not modify DHCP, interface or TFTP-root configuration. See [`PXE_RUNTIME.md`](PXE_RUNTIME.md).

## HTTP surface

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/healthz` | Service and storage health. |
| `GET` | `/boot/discovery.ipxe` | Headless iPXE discovery bootstrap. |
| `GET` | `/api/v1/discovery.ipxe` | Stock-iPXE query-string check-in returning an iPXE decision script. |
| `POST` | `/api/v1/discovery.ipxe` | Form-encoded compatibility check-in returning an iPXE decision script. |
| `POST` | `/api/v1/discovery` | JSON or form-encoded discovery API returning a typed JSON decision. |
| `GET` | `/api/v1/machines` | Read-only machine inventory. |
| `GET` | `/api/v1/machines/{id}` | Machine detail and identity observations. |
| `GET` | `/api/v1/machines/{id}/events` | Machine audit/discovery events. |
| `GET` | `/ui/` | Read-only discovery dashboard. |
| `GET` | `/ui/machines/{id}` | Read-only machine detail and event timeline. |

The initial UI intentionally has no administrative mutation endpoints. Operator authentication/authorization must exist before policy-changing Studio actions are exposed.

## Discovery payload

The 0.0.3 bootstrap submits only bounded observations:

- `mac`: current iPXE network-interface MAC address,
- `smbios_uuid`: iPXE `${uuid}` observation when available,
- `architecture`: iPXE build architecture observation,
- `firmware`: iPXE firmware platform observation.

MAC and SMBIOS UUID are identity observations, not credentials. AegisPXE does not place secrets in the discovery request.

The default bootstrap intentionally uses only stock iPXE scripting features. It chains a dynamic HTTP URL and expands the observations directly into the query string:

```text
/api/v1/discovery.ipxe?mac=${net0/mac}&smbios_uuid=${uuid:uristring}&architecture=${buildarch:uristring}&firmware=${platform:uristring}
```

This avoids a runtime dependency on the optional iPXE `PARAM_CMD` build option. Distribution-provided iPXE binaries therefore do not need to provide the `params` or `param` commands. POST remains accepted as a compatibility transport for custom clients.

The JSON/form discovery decoder is limited to 8 KiB for request bodies. Query-string observations are still subject to the same machine-domain validation and per-source discovery rate limit.

Upstream iPXE references:

- https://ipxe.org/appnote/scripting
- https://ipxe.org/cfg/mac
- https://ipxe.org/cmd/params
- https://ipxe.org/buildcfg/param_cmd

## Decision contract

0.0.3 has no InstallationSpec domain yet, therefore no discovery request can receive provisioning material.

| Machine policy | 0.0.3 decision | Reason |
| --- | --- | --- |
| `pending` | `local` | `pending_approval` |
| `local` | `local` | `local_policy` |
| `provision` | `local` | `installation_not_armed` |
| `blocked` | `blocked` | `machine_blocked` |

`provision` deliberately fails closed until a later milestone can prove that an immutable, armed InstallationSpec exists. No seed, profile, token, kernel, initrd or installer URL is exposed in 0.0.3.

The returned iPXE script exits successfully after recording and displaying the server decision. A failed discovery chain also exits rather than dropping into an operating-system selection menu.

## Security boundaries

Discovery is a low-privilege unauthenticated boundary because an unknown machine must be able to announce itself before it has credentials.

The endpoint may only create/update bounded machine observations and append their audit event. It cannot:

- approve or configure a machine,
- mutate machine policy,
- create or arm an installation,
- select an OS/profile,
- retrieve seeds or secrets.

Additional 0.0.3 controls:

- 8 KiB request-body limit for POST/JSON transports,
- per-source discovery window limit,
- bounded identity metadata,
- identity-conflict failure instead of silent merging,
- request correlation IDs,
- structured policy-decision logs,
- browser security headers,
- loopback service binding by default.

`PXE001_DISCOVERY_RATE_LIMITED` is returned to JSON clients that exceed the discovery request window. iPXE clients receive a non-provisioning exit script.

## Studio

The embedded Studio uses Go server-side rendering and ships inside the same `aegispxe-server` binary. It has no JavaScript framework or separate frontend service.

The dashboard shows:

- known-machine count,
- policy counts,
- machine ID,
- policy,
- architecture/firmware observations,
- first/last seen timestamps.

The machine detail view shows stored identifiers and the append-only machine event timeline. The views auto-refresh every five seconds so a newly booted test VM becomes visible without a manual page reload.

## Package E2E gate

The package-smoke job must exercise the installed `.deb`, not a source-tree server:

1. install the package and resolve its PXE runtime dependencies,
2. verify the packaged TFTP asset bootstrap and its non-overwrite behavior,
3. start the packaged binary against isolated SQLite state,
4. verify `/healthz`,
5. verify the generated iPXE bootstrap does not require `PARAM_CMD`,
6. submit the same discovery observation 20 times over the stock-iPXE GET/query transport,
7. assert exactly one `pending` machine exists,
8. assert exactly 20 machine discovery/seen events exist,
9. assert the machine is rendered by `/ui/`.

A real disposable-VM PXE run remains the final 0.0.3 environment gate before beginning Debian 13 provisioning.
