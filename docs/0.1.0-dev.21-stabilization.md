# 0.1.0-dev.21 stabilization audit

## Purpose

`0.1.0-dev.21` is a stabilization slice, not a feature-expansion slice. It was opened after the reporter/initramfs delivery experiments in dev.14 through dev.20 repeatedly failed on the real Proxmox UEFI/vTPM Debian fixture before `INSTALLER_STARTED`.

The rule for this slice is deliberately conservative:

> Keep only behavior that is either E2E-proven on the real deployment path or isolated behind a production boundary until it is proven.

## Installer rollback

The Debian 13 production boot contract is restored to the last real-VM-proven path:

```text
verified Debian kernel
verified native Debian initrd.gz
installation-scoped preseed.cfg
boot
```

The following unproven reporter delivery mechanisms are removed from the production path:

- iPXE magic-initrd file injection,
- explicitly named multi-initrd EFI handoff,
- server-generated newc overlay handoff,
- concatenated compressed + raw initramfs members,
- fully repacked reporter initramfs.

The Debian Preseed no longer invokes the reporter. The production `.deb` no longer ships the reporter executable. Trust/reporter protocol source remains available for isolated testing, but its HTTP APIs are not reachable from production PXE or Studio listeners.

A regression test locks the known-good Debian script/Preseed shape so a future trust implementation cannot silently replace the installer transport again.

## Repository audit scope

The stabilization review covered the primary RC trust and failure surfaces:

- PXE and Studio listener separation,
- request correlation,
- machine discovery and policy,
- immutable InstallationSpec and assignment state,
- Debian driver rendering,
- artifact resolution and integrity verification,
- operator authentication, Passkeys, sessions, recovery and CSRF,
- trusted reverse-proxy handling,
- TPM trust and reporter telemetry primitives,
- SQLite schema and migrations,
- event/log persistence and redaction,
- package install/upgrade behavior,
- systemd sandboxing,
- Studio log APIs,
- destructive data management,
- CI/static/race/vulnerability gates.

This is a manual repository-wide audit performed in the ChatGPT GitHub environment. It is not represented as a formal Codex Security repository scan.

## Findings fixed in dev.21

### Installer transport regression

**Severity:** blocker

Reporter injection had replaced a previously working Debian boot path with several successively more complicated initramfs handoff mechanisms. All passed source tests but failed the real UEFI/vTPM path.

**Fix:** all unproven boot transport code was removed from the production handler/package and Debian was restored to the last known-good path.

### Studio source trust exposed core inventory without an AegisPXE session

**Severity:** high

The Studio outer allowlist exposed `/api/v1/machines*` after only the trusted source/proxy transport gate. That contradicted the current human-authentication model in which trusted proxy source/identity is not itself an AegisPXE user session.

**Fix:** production Studio now exposes only `/ui/*` and `/healthz`. Inventory consumed by Studio is served through session-authenticated `/ui` handlers.

### Dormant trust/reporter APIs remained production-reachable

**Severity:** high while reporter runtime is suspended

Trust enrollment/challenge/proof and signed reporter telemetry endpoints were still allowlisted on the cleartext PXE listener even though no E2E-proven reporter delivery path existed.

**Fix:** the endpoints remain compiled for isolated tests but are no longer reachable from production listeners until the runtime path is proven.

### WebAuthn ceremony map had no hard capacity

**Severity:** medium

Five-minute WebAuthn ceremony state was cleaned by expiry but had no upper bound. Repeated ceremony starts could consume process memory.

**Fix:** active ceremony storage is bounded and expiry cleanup occurs before allocation. Tests cover the bound and reclamation.

### Recovery ticket map had no hard capacity

**Severity:** medium

Successful recovery Passkey flows could accumulate unconsumed five-minute recovery tickets.

**Fix:** recovery ticket storage is bounded, expired state is reclaimed, and tickets remain one-time. Tests cover capacity and replay.

### Operator session map had no hard capacity

**Severity:** medium

Authenticated users could create repeated eight-hour sessions with no process-level maximum.

**Fix:** active sessions are bounded and expired sessions are reclaimed before new allocation. Tests cover the limit and expiry cleanup.

### Session cookie Secure behavior depended on synthetic TLS mutation

**Severity:** defense-in-depth

The cookie setter inspected `r.TLS` directly even though the canonical application policy is `secureTransport(r)`. The trusted-proxy wrapper currently synthesizes TLS state, so the deployed path was protected, but the cookie contract was coupled to an implementation detail.

**Fix:** session set/clear now use the same `secureTransport` decision as authorization.

### Stale package-managed iPXE assets survived upgrades

**Severity:** medium operational / future Secure Boot blocker

The package installer intentionally left an existing `ipxe.efi` or `undionly.kpxe` unchanged when its bytes differed from the packaged source. A package upgrade could therefore leave an older bootloader indefinitely, and a future signed Secure Boot asset could fail to replace an older unsigned file.

**Fix:** package-managed regular boot assets are refreshed atomically when bytes differ. Symlink and non-regular targets fail closed. Package smoke deliberately corrupts an asset and verifies the installer restores the packaged bytes.

### Studio live-log cursor accepted malformed input as sequence zero

**Severity:** low

An invalid `after` cursor silently behaved like `after=0` in one live-log handler.

**Fix:** malformed cursors now return HTTP 400.

### NDJSON export Content-Disposition was malformed

**Severity:** low

The export header contained literal escaping from an earlier raw-string implementation.

**Fix:** the attachment filename is emitted as valid `Content-Disposition` and the response carries `nosniff`.

### Duplicate ADR number

**Severity:** documentation/architecture integrity

Two different accepted decisions were named ADR 0005.

**Fix:** layered human authentication is now ADR 0008; ADR 0005 remains the one-shot public boot handoff decision. References were updated.

## Management requirements added during stabilization

These are deliberately small and guarded because they are operationally necessary for repeated E2E work.

### Machine nicknames

Machines now have non-authoritative display nicknames:

- stored separately from immutable machine identity,
- trimmed,
- maximum 80 Unicode code points,
- control characters rejected,
- nickname changes audited,
- trust and discovery continue to use machine ID/MAC/SMBIOS identifiers only.

### Installation deletion

Administrator-only deletion requires the exact Installation ID as confirmation. An `ARMED` installation cannot be deleted until its assignment is cancelled. Correlated runtime state is removed transactionally and a system-level deletion audit event remains.

### Machine deletion

Administrator-only deletion requires the exact Machine ID. A Machine cannot be deleted while any InstallationSpec still references it. Discovery may recreate a deleted client on a later PXE boot, which is intentional.

## Existing controls reviewed and retained

The audit found the following existing controls materially sound and retained them:

- SQLite foreign keys, WAL mode and busy timeout,
- single database connection for deterministic SQLite transaction behavior,
- one armed assignment per Machine,
- immutable InstallationSpecs,
- strict Debian artifact source/path/provenance validation,
- signed Debian release metadata verification with `gpgv`,
- digest verification before artifact use,
- bounded artifact HTTP download size and redirect host restrictions,
- bounded discovery rate state,
- CSRF on authenticated browser mutations,
- constant-time recovery-key and CSRF comparisons,
- trusted direct-peer validation before accepting proxy headers,
- strict systemd service sandboxing and zero Linux capabilities,
- structured logging with sensitive-key redaction,
- bounded in-memory Studio log ring,
- bounded installer telemetry bodies/log chunks in the dormant reporter design.

## CI gates added/strengthened

The pull-request lane now includes:

1. `gofmt`,
2. `go test ./...`,
3. `go vet ./...`,
4. `go test -race ./...`,
5. official `govulncheck` against the Go vulnerability database,
6. binary/version build verification,
7. Debian package install smoke,
8. service health verification,
9. package-managed PXE asset refresh verification,
10. confirmation that the unproven reporter executable is absent from the production package.

## Remaining RC blockers

The following are intentionally not disguised as completed work:

### 1. Real Debian rollback E2E

Before dev.21 may be merged/released, the real Proxmox test VM must again reach and complete the Debian Installer using the restored boot path, then reboot through the deterministic local-boot chain.

### 2. Reporter delivery redesign

TPM trust and signed telemetry primitives are not sufficient by themselves. A reporter delivery mechanism must be designed around the proven installer path and pass the real UEFI/vTPM E2E before authenticated runtime lifecycle reporting is declared complete.

### 3. Secure Boot

The current package consumes the distribution's `/usr/lib/ipxe/ipxe.efi` and does not yet establish or verify a complete Secure Boot chain. Secure Boot needs a dedicated design/gate covering the exact iPXE binary, firmware trust, Debian kernel handoff and any future reporter delivery path. No silent downgrade is acceptable.

### 4. Long-run E2E matrix

Before `0.1.0-rc.1`, run repeated unattended installs plus deliberate failure cases and verify that package upgrade/migration from the deployed dev line preserves configuration and database state.

## Lower-priority cleanup candidates

These should not destabilize the restored installer path merely to make the repository prettier:

- remove the now-unused legacy Studio log handlers after their replacements have soaked,
- remove semantic Dashboard `Recent activity` collection rather than hiding that panel through presentation rules,
- replace client-side Machine log filtering with a server-side machine-scoped log endpoint,
- revisit one-shot consumption semantics around a response write failure,
- strengthen the future reporter design beyond a database-held symmetric HMAC verifier if the threat model requires database-compromise resistance,
- revalidate boot-trust duplicate-proof semantics when the reporter runtime is re-enabled.
