# ADR 0006: Authenticated installer telemetry

- Status: Accepted
- Date: 2026-08-19

## Context

AegisPXE can now complete a Debian 13 installation and uses a one-shot public boot handoff so a consumed installation does not automatically run again on the next PXE boot.

Scheduling state is not runtime state. `ARMED` and `CONSUMED` describe whether a destructive boot payload may be handed out. They do not prove that the installer started, prepared storage, installed the operating system, applied a profile, hardened the machine, validated the result, or completed successfully.

The Studio therefore needs authoritative installer telemetry rather than inferred progress. Installer logs must also be correlated to the immutable InstallationSpec so a failed run can be diagnosed without treating global server logs as the source of truth.

## Decision

### 1. Canonical lifecycle stages

The first stable lifecycle vocabulary is:

1. `CREATED`
2. `QUEUED`
3. `PXE_BOOTED`
4. `INSTALLER_STARTED`
5. `DISK_PREPARATION`
6. `OS_INSTALLING`
7. `PROFILE_APPLYING`
8. `HARDENING`
9. `FIRST_BOOT` when a post-install finalizer is required
10. `VALIDATING`
11. `SUCCESS`

`FAILED` is a terminal alternative for runtime failure.

The lifecycle is monotonic. A report may not regress to an older stage or skip a required boundary. Repeated delivery is handled through installation-scoped idempotency keys rather than by accepting duplicate state transitions.

### 2. Source authority

Lifecycle sources are explicit:

- `server` owns `CREATED`, `QUEUED`, and `PXE_BOOTED`.
- `installer` owns installer-runtime stages through `HARDENING`.
- `finalizer` owns `FIRST_BOOT` and may participate in final validation.
- `validator` owns validation and terminal success.

A source cannot claim a stage outside its authority. The server must never infer installer progress from kernel, initrd, artifact, Preseed, UI, or log reads.

### 3. Installation-scoped authentication

Installer telemetry endpoints require an installation-scoped lifecycle credential.

Credential properties:

- generated by the server with cryptographically secure randomness,
- scoped to exactly one immutable InstallationSpec,
- stored only as a SHA-256 verifier, never as the raw credential,
- bounded lifetime,
- revocable,
- automatically revoked on a terminal lifecycle state,
- transmitted only in the `Authorization` header when the telemetry API is used,
- never placed in URLs, query strings, public boot scripts, kernel arguments, ordinary logs, machine metadata, or the public Preseed.

The storage and HTTP authentication machinery may exist before credential release is enabled. Actual credential release remains behind the cryptographic boot-trust boundary established by ADR 0003. This ADR does not authorize embedding a credential into public PXE material as a temporary shortcut.

### 4. Telemetry event ingestion

The event endpoint accepts one strict JSON object per request and requires an `Idempotency-Key` header. Unknown fields are rejected.

Each accepted event records:

- installation ID,
- monotonic server event sequence,
- stage,
- source,
- server receive time,
- optional client time,
- request ID,
- idempotency key,
- bounded human-readable message,
- stable error code for `FAILED`,
- bounded non-sensitive metadata.

Reusing an idempotency key with identical content returns the existing event. Reusing it with different content is a conflict.

### 5. Installer log ingestion

Installer log uploads are installation-scoped and authenticated by the same lifecycle credential.

Each log chunk has:

- an installation-local contiguous sequence number,
- an idempotency key,
- an explicit source,
- server and optional client timestamps,
- a bounded payload,
- a SHA-256 digest computed after server-side redaction.

The initial limits are 128 KiB per chunk and 16 MiB per installation. Sequence gaps are rejected so missing chunks cannot be mistaken for a complete log stream.

Known sensitive line patterns are redacted before durable persistence. This is defense in depth and does not permit callers to intentionally send secrets.

### 6. Scheduling remains separate

ADR 0005 remains authoritative for one-shot scheduling. The assignment is consumed when the final public boot payload is handed to the installer. That consumption does not produce `INSTALLER_STARTED` or `SUCCESS`.

Likewise, a lifecycle terminal state does not retroactively redefine assignment history.

### 7. Local boot after provisioning

When the machine has no armed installation, AegisPXE should actively attempt local boot rather than merely returning from iPXE and depending on firmware boot-order behavior.

For x86_64 UEFI the boot path attempts Debian vendor loaders, the standard fallback `\\EFI\\BOOT\\BOOTX64.EFI`, and then a generic matching local disk. Legacy BIOS uses the local disk boot path. Only if all local boot attempts fail does AegisPXE return failure to firmware.

## Consequences

- The Studio can display real installation progress without guessing.
- Reboot behavior no longer depends solely on firmware correctly continuing after an iPXE `exit`.
- Installer logs become attached to the installation that produced them.
- Telemetry retries are safe and deterministic.
- A stolen discovery identifier remains insufficient to submit trusted installer state.
- Telemetry is not considered end-to-end usable until cryptographic boot trust releases the installation credential through an approved secure channel.
