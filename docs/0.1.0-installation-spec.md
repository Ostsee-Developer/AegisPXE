# 0.1.0 Debian 13 Standard: InstallationSpec foundation

`0.1.0-dev.1` introduced the immutable installation contract. `0.1.0-dev.2` strengthened the artifact snapshot with trusted source/provenance metadata produced by the Debian 13 resolver. `0.1.0-dev.3` completed the boundary needed for deterministic typed BootSpec rendering. `0.1.0-dev.4` makes the selected profile self-contained and pins the destructive target disk needed by a real unattended installer.

## Contract

An InstallationSpec is a server-created immutable snapshot for one provisioning attempt. It pins:

- machine identity,
- driver ID and independent driver contract version,
- OS release and architecture,
- profile ID and immutable profile revision,
- resolved versioned ProfileSnapshot rather than a future live profile lookup,
- artifact identities, names, versioned HTTPS sources, installer versions, canonical SHA-256 digests, byte sizes and provenance,
- storage intent including an explicit whole-device `TargetDisk`,
- security intent,
- lifecycle credential identity, never the credential secret,
- creation timestamp and actor.

Artifact IDs and artifact names are unique within a spec so downstream drivers never have to guess which artifact owns a role.

The store exposes create and read operations only. There is deliberately no update operation. A different desired state creates a different InstallationSpec.

## Resolved profile rule

The driver must not reread a mutable or newer profile definition after an InstallationSpec exists. The selected profile revision is resolved into the versioned ProfileSnapshot stored in that spec. Caller-owned slices are cloned before the snapshot crosses a persistence boundary.

ProfileSnapshot v1 contains the semantic identity, locale/timezone, SSH-public-key, sudo and package intent required by the Debian 13 Standard seed. It contains no private key, reusable password or lifecycle credential value.

## Target-disk rule

Destructive target selection is explicit per InstallationSpec. The initial contract accepts a bounded whole-device path such as `/dev/vda`, `/dev/sda` or `/dev/nvme0n1` and rejects partition paths such as `/dev/vda1`.

The driver may not substitute a different device because enumeration order changed. Unsupported storage forms fail before rendering.

## Security boundary

This slice does not expose `CreateInstallationSpec` through HTTP or the Studio. Creating or arming an installation is an administrative action and remains unavailable until AegisPXE has an explicit authenticated operator boundary.

Lifecycle credential values are not part of the spec. Only the non-secret credential identity is pinned so later components can resolve the secret through the dedicated secret-storage boundary.

Artifacts must carry a stable identity, versioned HTTPS source, installer version, byte size, provenance and a canonical `sha256:<64 lowercase hex>` digest. The Debian 13 driver may only use those fields after completing the signed-release and content-verification chain documented in `docs/0.1.0-artifact-verification.md`.

## Driver-version rule

`DriverVersion` is the driver's own behavioral contract version, not the AegisPXE application version. A driver must refuse a spec requiring a different driver contract version rather than silently reinterpret it with newer behavior.

The initial Debian 13 driver contract is ID `debian13`, version `1`.

## Relationship to BootSpec and SeedBundle

The InstallationSpec remains authoritative. A BootSpec and native SeedBundle are rendered deterministically from it and are not persisted as competing desired-state records. See `docs/0.1.0-boot-spec.md` and `docs/0.1.0-debian-preseed.md`.

## Audit and logging

Spec creation and its `INSTALLATION_CREATED` event are committed atomically. Operational logs record IDs, driver/profile revisions, snapshot schema version and actor, but never lifecycle credential material or SSH-key values.

Schema migration from the pre-ProfileSnapshot database is explicit and logged with `component=store.schema`, `operation=migrate`, old/new schema versions and result. Migration does not invent historical profile intent for already persisted records.

## Gate for the foundation

- invalid specs fail closed,
- a spec references an existing machine,
- installation ID and creation time are server-assigned,
- verified artifact identity, source, version, digest, size and provenance are mandatory,
- artifact IDs and names are unique,
- resolved profile intent and target disk are part of the immutable snapshot,
- caller mutation after creation cannot alter the persisted snapshot,
- reading the spec round-trips the exact immutable snapshot,
- creation emits exactly one auditable `INSTALLATION_CREATED` event,
- no administrative HTTP mutation endpoint exists yet.
