# 0.1.0 Debian 13 Standard: unattended seed

`0.1.0-dev.4` introduced the deterministic Debian 13 Standard seed renderer. `0.1.0-dev.6` connects that SeedBundle to the assignment-gated iPXE boot path using native initrd preseeding.

## Supported driver contract

Debian driver `debian13` version `1` currently accepts only the Standard vertical slice:

- Debian 13 amd64,
- unencrypted `whole-disk` storage,
- ext4,
- explicit whole-device target disk,
- root login disabled,
- SSH password authentication disabled,
- automatic security updates enabled,
- SSH-key-only administrative account,
- explicit passwordless sudo for that administrator.

Unsupported desired state fails with `DRV001_DRIVER_SPEC_UNSUPPORTED`. The driver never silently approximates encryption, authentication or storage policy.

## Preseed output

The rendered SeedBundle starts with Debian's canonical `#_preseed_V1` marker and pins native installer values for:

- locale, keyboard and timezone,
- DHCP/network interface selection and immutable hostname,
- Debian package mirror,
- explicit partitioning target,
- regular whole-disk atomic layout,
- explicit GRUB target,
- standard task and requested packages,
- OpenSSH server, sudo and unattended-upgrades,
- SSH-key-only administrator creation,
- sudoers validation,
- sshd configuration validation,
- automatic update configuration,
- final reboot.

Debian Installer creates the normal administrative user natively with `passwd/user-password-crypted` set to `!`, so the account remains disabled during installation. The late hook installs the pinned SSH keys, sudoers policy and sshd hardening first, then changes the shadow password field to the non-locking unusable `NP` marker. OpenSSH password and keyboard-interactive authentication remain disabled, so the account is usable through public-key authentication without introducing a reusable password secret.

## Seed security and transport

The SeedBundle contains installation configuration and SSH public keys but no lifecycle credential value, reusable password, private key or recovery secret. Normal operational logs never contain SeedBundle content or public-key values.

Debian Standard uses **initrd preseeding without custom archive repacking**. The assignment-gated iPXE boot script performs three public reads:

1. the verified Debian kernel,
2. the verified Debian `initrd.gz`,
3. the rendered `preseed.cfg`.

iPXE loads the normal installer initrd, then injects the fetched Preseed as `/preseed.cfg` in its magic initrd. Debian Installer automatically consumes that root-level file as initrd preconfiguration.

AegisPXE therefore does not use Debian `preseed/url` for the Standard path and does not create a custom CPIO/gzip builder. The BootSpec exposes the relative non-secret `SeedRef` `preseed.cfg`; the HTTP transport binds it to the currently armed InstallationSpec path.

The Preseed endpoint is classified as non-secret public boot material. It is available only when the Machine is operator-approved and the exact InstallationSpec is armed. Lifecycle credentials and authenticated installer APIs remain behind the separate cryptographic boot-trust boundary.

Rendering or fetching the seed/initrd is not an installer lifecycle event and never implies `INSTALLER_STARTED`.

## Artifact boundary

The verified HTTP artifact loader fetches only the Descriptor pinned inside the immutable InstallationSpec, bounds response size, restricts redirects to the pinned origin, and verifies exact byte size plus SHA-256 before returning content.

The loader is not an unauthenticated general-purpose proxy. In dev.6 its kernel/initrd HTTP routes first enforce the same Machine policy + armed Assignment gate as the boot script and Preseed endpoint.

Fetching or verifying an artifact does not advance installation lifecycle state or consume the Assignment.

## Observability

Operational seed render logs use:

- `component=driver.debian13`,
- `operation=render_seed`,
- `request_id`,
- `machine_id`,
- `installation_id`,
- driver/profile revisions,
- normalized target disk,
- rendered byte count,
- `result`,
- stable `error_code` on failure,
- `duration_ms`.

Public boot transport logs use `component=httpapi.provisioning` and distinguish `serve_boot_script`, `serve_preseed` and `serve_artifact`. They include request, Machine, Installation and Assignment correlation, result/duration and stable failure codes. The verified artifact loader additionally records artifact ID/name/digest and verified byte count.

Seed content, artifact content, SSH-key values and credential material are never intentional log fields.

## Tests

The focused tests prove:

- target disk is rendered into both partitioning and GRUB configuration,
- native disabled-user creation and key-only administrator hardening are present,
- generated Preseed starts with `#_preseed_V1`,
- unsupported Standard state is rejected with a stable code,
- armed discovery chains the exact Installation boot script,
- the boot script uses iPXE magic-initrd injection for `/preseed.cfg`,
- boot/preseed/artifact reads do not consume the Assignment or invent installer lifecycle events,
- public provisioning logs contain correlation data but not credential, SSH-key or SeedBundle content,
- artifact hash mismatch fails closed with correlated logging.
